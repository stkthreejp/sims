SIMS · UI & Brand Guide

The visual contract
between design & engineering.

This document encodes every design decision that's been made for SIMS so far — tokens, components, layout, and the rationale behind them — in a single place a developer can read top-to-bottom and refer back to. It is the source of truth for anything visual.

The rule: nothing visual ships in code that isn't either documented here or added to tokens.css first. When you hit something this guide doesn't cover, raise it — don't invent.

01Design principles

Five rules that should sit behind every visual decision. If a screen is hard to design, return here.

01 · Density without clutter

Underwriters scan many rows of structured data per hour. Tables run at 13px body with 12px row padding — tight, not crammed. Whitespace is reserved for between cards and around the page edge, not inside dense data.

02 · One blue, used decisively

A single brand blue carries primary CTAs, focus, the active nav state, hover backgrounds, and Quoted status. Nothing else is colored "for fun." If a control isn't blue, it's neutral.

03 · Status is the loudest signal

A submission's state (Draft · In Progress · Quoted · Bound · Declined) is encoded twice: a pill and a row tint. Quoted is one shade darker than the others so it pops in scans.

04 · Numbers earn a monospace

IDs (SUB-2026-00418), timestamps, and tabular columns get Reddit Mono so digits align vertically. Body copy stays Inter. Don't put labels in mono — only identifiers and numbers.

05 · Elevation is barely there

One shadow exists (--shadow-sm). Cards sit on a faint shadow against a faint --bg. We do not have card-on-card, layered overlays, glassmorphism, or gradients beyond the single kpi-hero wash. The interface is flat with one half-step of depth.

02The token contract

tokens.css is the single source of truth. Everything in this guide either resolves to a token or is built from tokens. The names on this side and in the app's theme system must be identical — that's how design and code stay in sync.

Don't do this Reach for a raw hex in component code (color: #1B75BA). The next person who edits that file has no idea it's the brand blue, and a palette change won't find it.
Do this Always reference the token: color: var(--accent). If you need a value that doesn't exist, add it to tokens.css first, then use it. Propose the name + rationale in the same change.

Naming convention: we use semantic-purpose names, not literal color names. --accent-ink means “text on a soft-accent background,” not “dark blue.” This way the palette can shift without renaming the API.

20Density & rhythm

SIMS is a high-density workbench. Get the rhythm right and the whole interface feels “professional;” get it wrong and it feels either airless or cheap.

Vertical rhythm

BetweenGap
Page H1 → next block18px
Metric strip → toolbar/table18px
Major card → major card18–20px
Inside a card: header → body14px header padding + 0 (border) + body padding
Inside a card body: section → section16–22px

Table density

13px body, 12px 14px row padding, 1px --line-2 dividers. Do not loosen. Sparser tables feel like a marketing site, not an underwriting tool.

Card-on-page

Cards have --shadow-sm against a --bg page. Do not put a card inside another card — if a section needs visual separation inside a card, use an internal divider (1px solid var(--line-2)) and a slight padding bump, not a nested card.

22Voice & copy

Headings

Sentence case. Short. The thing itself, not a description of the thing. “Submissions”, not “Manage submissions.” “Coverage breakdown”, not “Here is the coverage breakdown.”

Eyebrow labels

UPPERCASE, 10.5px, 0.04em tracking, --ink-3. Three words max. OPEN PIPELINE PREMIUM, not “Open pipeline premium total.”

Buttons

Verb + object. New submission, Generate document, Bind quote. Never Submit or OK. Never trailing dots.

Empty / null

An em-dash in --ink-4. Not “N/A,” not blank. The dash means “there is intentionally no value here.”

Page subtitles

Factual, no marketing. “All submissions across your book · 42 records” — tells the user what they're looking at and how much of it there is. Skip if it doesn't add information.

Status labels

Two words max. Fixed vocabulary: Draft, In Progress, Quoted, Bound, Declined. Do not rename these in copy — they're the data contract.

23Spinning up a new page

When a screen comes in that isn't in the shipped mocks — or when you need to scaffold one before design catches up — use this. Every SIMS page is built from the same anatomy and resolves to one of four layout recipes. Follow the recipe, hit the tokens, and a new page will sit cleanly next to the existing ones without a design review.

Standard page anatomy

Five regions, top to bottom. The first three are the same on every page. The bottom two are where the page differs.

Quick checklist before shipping a new page

  1. Breadcrumb in topbar with the correct trail and bolded current page.
  2. H1 in sentence case, 22–24px / 600, with a concrete subtitle.
  3. Page-level actions on the right of the head — max one primary.
  4. Every metric / table cell that holds a number uses tabular-nums.
  5. Every status uses a pill from the locked vocabulary — no new labels.
  6. Every icon is the stroke style at 1.7 weight, inherits currentColor.
  7. Empty + loading + error states all present.
  8. At <980px the sidebar collapses to a horizontal scroll strip; at <1180px two-column detail layouts stack.
  9. No raw hex anywhere — every color is a token reference.
  10. No new tokens introduced without adding them to tokens.css first.

24Avoid this

Patterns that look fine in isolation but break the SIMS feel. If you catch yourself reaching for one, pause.

No gradients (except the dashboard hero KPI) The interface is flat. linear-gradient(...) on a card, button, or chart background is wrong. The one exception is the optional --accent-soft→--surface wash on the hero KPI tile.
No second blue, no purples, no teals We have one accent (--accent) with five variants. Charts, status, decorations, all use this family. Resist pulling in a separate “chart palette” without a token proposal.
No 14px+ button heights or oversized CTAs Buttons are 32 / 26 / 24px. A big bouncy CTA pulls the eye away from data, which is what the user came for.
No emoji in UI Status, severity, and counts are encoded with pills and color. Emoji are decorative noise in an underwriting context.
No nested cards or card-in-card shadows Inside a card, use a 1px --line-2 divider and padding, not another bordered box.
No body copy on --ink-4 That's a placeholder / null tone. Sustained reading on it fails contrast.
No new tokens silently introduced in code If the design here doesn't cover what you need, raise it. Add to tokens.css first — with a name and a rationale — then reference it. One unsanctioned hex in a vacuum is how design systems die.
When in doubt Use --ink-2 for text, --line for the border, --r-md for the radius, --shadow-sm for elevation, --s-4 for the gap. Those defaults are right ~80% of the time.
