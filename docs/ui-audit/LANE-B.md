# Lane B — Billing & Accounting UI findings

**B1 [P0] — Cash application cannot post partial applications; over/short-paid receipts dead-end** — `frontend/src/pages/billing/CashApplicationPage.tsx:192-195, 323-326` — `canPost` requires `isBalanced` (gross applied must exactly equal receipt remaining to the half-cent), yet the domain supports `PartiallyApplied` receipts (ReceiptsPage RECEIPT_PILL, `openReceipts` filter includes it). A wire that exceeds total open invoices, or a deliberate partial application, can never be posted — cash sits in "Open" forever with no override. — Fix: allow gross applied ≤ receipt remaining, warn (don't block) on under-application (S).

**B2 [P0] — Statement reconciliation has no manual-match UI, so any unmatched line permanently blocks posting** — `frontend/src/pages/billing/StatementReconciliationPage.tsx:152-159, 162, 216-228, 246-250` — `setLineMatch` is only ever called with `null` (clear match); the API supports `invoiceLineId` and the `ManualMatched` badge exists, but there is no picker to match a line. Footer says "resolve before posting" while the UI offers no way to resolve — `canPost` requires `unmatchedCount === 0`, so the statement is stuck at `Imported` forever. — Fix: add an invoice-line picker per unmatched row calling `payeeStatementsApi.setLineMatch(id, lineId, invoiceLineId)` (M).

**B3 [P0] — Statement import requires guessing a raw "AP Ledger Account ID"** — `frontend/src/pages/billing/StatementReconciliationPage.tsx:39, 89-92` — Required field is a bare number input with placeholder "e.g. 42"; accounting staff have no way to know internal ledger-account PKs, and a wrong ID posts reconciliation JEs against the wrong GL account (or fails opaquely via B10-style toast). — Fix: replace with a ledger-account dropdown fetched from the chart of accounts (S/M).

**B4 [P0] — 401-refresh interceptor silently replays money POSTs with no idempotency key** — `frontend/src/api/client.ts:38-45, 53-59`; mutations in `receipts.api.ts:10-17`, `invoices.api.ts:10-11`, `cashDistribution.api.ts:21-25`, `disbursements.api.ts:24-31`, `payeeStatements.api.ts:26-27`, `periodClose.api.ts:19-26` — Both the queued-retry path and the `_retry` path re-issue the original request after refresh; none of the billing clients send an `Idempotency-Key`. Most exposed: `applyCash`, `createBatch`, `markExecuted` (posts sweep JEs), `postDisbursement`, `createInvoice`, `createReceipt` — a replay after a processed-but-401-raced request double-posts GL entries or double-pays a carrier. — Fix: generate a per-mutation idempotency header in `apiClient` for POSTs and honor it server-side; at minimum never auto-replay non-GET (M).

**B5 [P0] — One-click "Post" on draft disbursement with no confirmation, and no void path on the page** — `frontend/src/pages/billing/DisbursementsPage.tsx:422-432` — Clicking the small "Post" button in the row immediately posts the payment JE (`postDisbursement`) with no confirm dialog or preview, unlike batch execution which has a modal. `voidDisbursement` is imported (line 11) but never used — undoing requires knowing to hunt the event down in Activity. Also no way to edit/delete a wrong Draft. — Fix: add a confirm modal showing payee/amount, and a void/delete action on Draft/Posted rows (S).

**B6 [P1] — Manual invoice "Post Invoice" computes fees sight-unseen from free-text LOB that must exactly match fee rules** — `frontend/src/pages/billing/InvoicesPage.tsx:76-79, 117-119, 42` — Line of Business is free text with placeholder "e.g. GL, Commercial Auto"; fee-rule applicability matches on exact strings, so a typo or the placeholder's own suggestions silently produce missing/wrong tax and stamping fees. There is no fee preview — create and GL posting happen in one click ("Invoice X posted"). — Fix: LOB dropdown sourced from fee-rule LOB values + a fee preview step before posting (M); verify by creating an invoice with LOB "GL" vs the rule's stored value and comparing fee lines.

**B7 [P1] — Invoices "Outstanding" metric is wrong once anything is partially paid** — `frontend/src/pages/billing/InvoicesPage.tsx:312-315` — `outstanding` sums full `totalAmount` of invoices with `status === 'Posted'` only: partially-paid invoices drop out of the metric entirely and posted ones count at gross even after partial application (open balance lives on `/cash-application/open-invoices`, not used here). The number the accountant reconciles against the bank is simply not receivables. — Fix: have the summary endpoint return openBalance, or sum `openBalance` across Posted+PartiallyPaid (S).

**B8 [P1] — InvoicesPage passes raw domain status to StatusBadge; `PartiallyPaid`/`Paid` render as unstyled pills** — `frontend/src/pages/billing/InvoicesPage.tsx:152, 435`; `frontend/src/components/common/StatusBadge.tsx:8`; `frontend/src/index.css:483-500` — StatusBadge uses `sd-pill ${status.toLowerCase()}` as a CSS variant; CSS has no `.paid`/`.partiallypaid` class, so once cash is applied invoices show colorless badges. Every other billing page maps domain status → variant via a PILL record; InvoicesPage is the outlier. — Fix: add an `INVOICE_PILL` map like ReceiptsPage's (S).

**B9 [P1] — Half the billing mutations toast the axios default message, hiding the server's reason** — `CashDistributionPage.tsx:52, 262`; `DisbursementsPage.tsx:73, 382`; `PeriodClosePage.tsx:100, 111, 122, 299`; `SyncHealthPage.tsx:156, 253`; `ActivityPage.tsx:70`; `InvoicesPage.tsx:43` — `onError: (e: Error) => toast.error(e.message)` yields "Request failed with status code 409/500" (or InvoicesPage's fixed 'Failed to create invoice'), while CashApplication and payeeStatements correctly surface `err.response.data.errorMessage`. A period-close blocked server-side or a Postgres P0001 trap becomes an unexplained failure. — Fix: shared `extractApiError(e)` helper used by all billing onError handlers (S).

**B10 [P1] — Commission is hand-keyed per line (default 0%) with 4-decimal currency rounding** — `frontend/src/pages/billing/CashApplicationPage.tsx:21-27, 183, 110-117` — `commissionRate` defaults to 0 with no lookup from producer/agency commission schedules, so forgetting to type the rate over-remits to the carrier; `rowCommission`/`rowNet` round to 4 decimals (sub-cent) and `ApplicationLineRequest.commissionAmount` is sent as-is, while every display truncates to 2 — penny drift between UI totals and posted JEs. — Fix: prefill rate from the invoice's producer commission and round to 2 decimals before submit (M).

**B11 [P1] — Cash application shows every open invoice in the system, unfiltered by payer** — `frontend/src/pages/billing/CashApplicationPage.tsx:156-159, 292-316`; `receipts.api.ts:13-14` — `getOpenInvoices` takes no params; after selecting an agency's receipt the "Add invoices" chip list is all open invoices for all agencies/insureds with no search, so one misclick applies Agency A's wire to Agency B's invoice (recoverable only via Activity void). — Fix: filter/group open invoices by the receipt's payer, or at least add a text filter over the chips (M).

**B12 [P1] — Create Disbursement allows over-balance amounts and ambiguous cross-payee runs** — `frontend/src/pages/billing/DisbursementsPage.tsx:117-122, 63, 76-82` — Amount inputs have `max={p.balance}` (only blocks spinners, not typed values) and no over-balance highlight like cash app's `isOver`; user can pay a carrier more than owed. Selection can span multiple payees but `CreateDisbursementRequest` has one paymentDate/method/reference and `DisbursementSummary.payeeName` is singular — who receives the check is guesswork. — Fix: validate amount ≤ balance per line, and group/create one disbursement per payee with a preview (M).

**B13 [P1] — Trust balance is invisible exactly where money leaves the trust** — `frontend/src/components/accounting/CashBalanceBadge.tsx:14-30`; only rendered in `SyncHealthPage.tsx:365` — "Mark Executed" (posts trust sweeps) and disbursement posting never show the trust balance, so staff can't verify sufficiency before wiring; the badge also returns `null` on fetch error, silently hiding the balance rather than flagging staleness. — Fix: render CashBalanceBadge on CashDistribution/Disbursements headers and show an error state (S).

**B14 [P1] — Distribution batches cannot be voided or edited anywhere in the UI** — `frontend/src/pages/billing/CashDistributionPage.tsx:23-30` (BATCH_PILL includes `Voided`); `ActivityPage.tsx:52-59` (`Distribution` → "Void not supported") — If the wrong payees are batched, the instructions are locked out of the Pending Queue and there is no unbatch/void action; the `Voided` status implies the backend supports it. — Fix: add a "Void batch" action for Open/PdfGenerated batches (M); verify backend endpoint exists first.

**B15 [P1] — "Mark Batch Executed" confirmation never shows what is being executed** — `frontend/src/pages/billing/CashDistributionPage.tsx:398-438` — The modal that posts sweep JEs shows only prose and an optional bank ref — no batch number, total, or payee list — so the user confirms an irreversible trust movement blind (and can have a different batch's detail panel open beside it). — Fix: render batch number, wire count and total in the modal body from `getBatch` (S).

**B16 [P1] — No pagination, search, or server filtering on Invoices/Receipts/Activity/open lists** — `InvoicesPage.tsx:293-296`, `ReceiptsPage.tsx:204-207`, `ActivityPage.tsx:265-268`, `CashApplicationPage.tsx:151-159` — All lists fetch the entire table; Invoices and Receipts have zero filters (no status, payer, date, or number search), and "Total Billed (all time)" is computed client-side over the whole dataset. At production volume these pages become slow and unscannable. — Fix: add server-side paging + status/date/payer filters, mirroring ActivityPage's filter bar (L).

**B17 [P1] — Period close gates on a manually refreshed, possibly stale checklist; page state forks from cache** — `frontend/src/pages/billing/PeriodClosePage.tsx:93-95, 145-148, 165-171, 273-287` — Checklist is only evaluated when the user clicks "Refresh checklist"; `hasBlockers` then gates Close using results that may be minutes/days old (new postings since evaluation aren't reflected). Separately, `periods` is copied into local state via `useEffect` and mutated by `onUpdated`, so a background refetch silently overwrites panel state and multi-tab edits diverge. — Fix: auto-evaluate on period select and re-evaluate server-side inside close; drop local `periods` copy in favor of query cache (M); verify backend `close` re-runs blocking checks independently.

**B18 [P1] — Void button in Activity is shown to all billing users; admin gating is dead code, and gating model is role-vs-permission inconsistent** — `frontend/src/pages/billing/ActivityPage.tsx:121` (`isAdmin` computed, never used at lines 236-251); `PeriodClosePage.tsx:269`, `SyncHealthPage.tsx:339` (role `Admin`) vs `App.tsx:283-291` (permission `AccountingManage`) — Any user who can reach `/billing/activity` can void invoices/receipts/applications/disbursements (assuming backend allows), while period close/rollups use a hard-coded role check that ignores the permission system — an AccountingManage user sees Period Close but no close button and no explanation. — Fix: gate all destructive billing actions on one permission (e.g. `AccountingManage` or a new `AccountingVoid`) and delete the unused `isAdmin` (S); verify backend authorization on the void endpoints.

**B19 [P1] — Rollup "Resync" re-exports with no confirmation regardless of status** — `frontend/src/pages/billing/SyncHealthPage.tsx:320-329` — Resync is a single click on every row including `Posted`/`Exported` rollups; if the backend re-posts manual journals to Xero non-idempotently this duplicates a month of JEs in the books. No warning distinguishes "retry a Failed export" from "re-send a Posted one". — Fix: confirm dialog for non-Failed rollups stating consequence (S); verify backend resync idempotency by resyncing a Posted rollup in test.

**B20 [P1] — Invoice/receipt detail views are unrouted component state; errors render a blank screen** — `InvoicesPage.tsx:128-135, 305-307`; `ReceiptsPage.tsx:91-98, 216` — Detail is toggled via `selectedId` state: browser Back leaves the whole page, refresh loses context, and nothing (statements, activity, cash app) can deep-link to an invoice. On fetch error `!inv`/`!receipt` returns `null` — a blank page with no back affordance or retry. — Fix: promote to routes (`/billing/invoices/:id`) and add an error state with Back (M).

**B21 [P2] — Receipt → application → distribution workflow has no navigational continuity** — `ReceiptsPage.tsx:133-138` ("Use Cash Application to match invoices" — no link), `CashApplicationPage.tsx:148` (no receiptId param), `CashApplicationPage.tsx:164` (success toast, no link onward to Cash Distribution) — Each stage tells the user the next stage exists but makes them re-find the receipt by eye in another page's list; with several same-day wires from the same payer this invites applying against the wrong receipt. — Fix: "Apply cash" button on receipt rows/detail navigating to `/billing/cash-application?receiptId=` and a post-apply link to the pending queue (M).

**B22 [P2] — Past-due logic hard-codes 30 days from invoiceDate and ignores dueDate** — `frontend/src/pages/billing/InvoicesPage.tsx:309-317, 413-418` — Aging/row-tinting uses `invoiceDate + 30/15d` while the payables side has a real `dueDate` field (`disbursement.types.ts:12`); receivable and payable aging therefore disagree, and terms other than net-30 misreport past-due amounts. — Fix: surface `dueDate` on InvoiceSummary and age against it (S).

**B23 [P2] — Void/reopen reasons optional on irreversible financial reversals** — `ActivityPage.tsx:89-99` (VoidModal "Reason (optional)"), `PeriodClosePage.tsx:236-241` (reopen reason optional) — Reversing GL entries and reopening closed periods with no recorded reason leaves audit-trail gaps an MGA's carrier audits will flag. — Fix: make reason required (non-empty) client-side for void and reopen (S).

**B24 [P2] — Icon-only / unlabeled controls in money flows** — `InvoicesPage.tsx:144-146` (ArrowLeft back, no text/aria-label), `StatementReconciliationPage.tsx:218-227` (X "clear match", title only), `CashDistributionPage.tsx:318-325` (FileText PDF, title only), modal `&times;` closes across pages (no aria-label) — Destructive-adjacent actions (clearing a match) look identical to close buttons. — Fix: add visible labels or aria-labels + tooltips consistently (S).

**B25 [P2] — Unkeyed fragments in expandable money tables** — `CashDistributionPage.tsx:160` and `DisbursementsPage.tsx:286` use `<>...</>` inside `.map`; the key sits on the inner `<tr>` not the fragment — React key warnings and risk of row/checkbox state mismatch when the payee list reorders after invalidation (selection checkboxes live in these rows). — Fix: use `<Fragment key={...}>` (S); verify via console warnings on the pending queue.

**B26 [P2] — Status badge and date conventions differ across the 9 pages** — Common `StatusBadge` with variant-mapping (Receipts/Disbursements/Activity), raw-status `StatusBadge` (Invoices), plus two local `StatusBadge` implementations (`PeriodClosePage.tsx:24-36`, `SyncHealthPage.tsx:23-37`); `CashDistributionPage.tsx:20-21` parses dates without the `'T00:00:00'` local-midnight guard used by the other six pages; SyncHealth uses hard-coded `hover:bg-gray-50`/`divide-gray-100` instead of theme vars. Same concept ("Partial" vs "PartiallyPaid" vs "PartiallyApplied") renders differently page to page. — Fix: consolidate on the shared StatusBadge + a shared `fmtDate`/`fmtMoney` util in one billing module (M).

**B27 [P3] — Numeric money inputs bound to parsed numbers fight the user** — `InvoicesPage.tsx:71-72`, `ReceiptsPage.tsx:68-69`, `CashApplicationPage.tsx:101-107` — `value={form.amount}` with `parseFloat(e.target.value) || 0` means clearing the field snaps to `0`, leading zeros stick, and typing "12." momentarily resets — friction when keying dozens of wire amounts. — Fix: keep string state for inputs, parse on blur/submit like DisbursementsPage's `amounts: Record<number, string>` (S).
