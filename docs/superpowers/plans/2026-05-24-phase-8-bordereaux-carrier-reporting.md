# Phase 8 Bordereaux and Carrier Reporting Slice Plan

Source plans:
- `docs/SIMS improvement 5.17.26.md`
- `docs/go-live-plan.md`

Assumption: Phase 8 is a go-live blocker only for carrier/programs that require bordereaux at launch. If no launch carrier requires bordereaux on day one, Phase 8 can continue after core go-live hardening, but each delivered slice still has to satisfy the relevant go-live security, authorization, UI, deployment, and smoke-test gates before release.

## Phase 8 Scope From The 5.17.26 Plan

Phase 8 exists because bordereaux requirements are carrier/program-specific and should sit on top of Program Configuration instead of one-off exports.

Required capabilities:
- Bordereaux profiles by carrier/program.
- Report types: premium first, then tax/fee and commission, with claims left for the later claims phase.
- Configurable frequency, output format, required columns, mapping rules, date basis, included transaction types, and validation rules.
- Bordereaux runs with profile id, period start/end, status, generated by, generated at, file location, and validation result summary.
- CSV/XLSX export generation.
- Validation for missing policy number, missing insured state, missing transaction type, missing premium/tax/commission values, unissued policy packets, unposted accounting, and transactions outside the reporting period.
- Reconciliation against carrier statements with accepted, rejected, corrected, and resubmitted states.

Acceptance criteria from the roadmap:
- SIMS can generate at least one carrier/program premium bordereaux from policy transaction data.
- Exported files are stored and traceable.
- Validation prevents obvious bad reports.

## Comparison To The Go-Live Plan

Phase 8 is not just a reporting feature. It touches several go-live risk areas:

- Go-live Phase 0: every slice must leave backend tests, frontend build, EF drift check, and dependency checks runnable.
- Go-live Phase 1: export files rely on production blob storage and signed download URLs, so production config must fail closed when storage is missing.
- Go-live Phase 2: bordereaux rows expose policy, insured, accounting, and report data, so endpoint authorization and data scope must be explicit.
- Go-live Phase 3: staging smoke tests must prove export generation, storage, download, and large-period behavior work outside local dev.
- Go-live Phase 4: Reports currently has coming-soon/polish issues; Phase 8 UI must not add another placeholder report.
- Go-live Phase 5: launch data must include active program/carrier setup, report profile setup, accounting mappings, and issued/postable policy transactions.
- Go-live Phase 6: final UAT needs an underwriter/accounting/admin walkthrough from profile setup through export download and reconciliation status.

## Execution Rules

- Work on `main`; do not create a feature branch or worktree.
- Each slice must be independently testable and useful.
- After each implementation slice:
  - run the slice-specific tests listed below,
  - run the minimum regression gate listed for that slice,
  - commit only that slice's files,
  - push `main`,
  - announce the next slice.
- Do not start the next slice if the current slice has failing tests, skipped verification, or unclear data behavior.
- Claims bordereaux is explicitly out of Phase 8 implementation unless the user changes scope; Phase 8 may reserve enum/config values for future claims but should not build claims logic.

## Slice 8.1: Bordereaux Domain Foundation

Goal: create the backend persistence model for profiles and runs without generating files yet.

Requirements:
- Add `BordereauxProfile` under the domain model.
- Add `BordereauxRun` under the domain model.
- Add enums or constrained strings for report type, frequency, output format, date basis, run status, and reconciliation status.
- A profile must belong to a program and carrier.
- A profile may optionally narrow to line of business and state only if current data patterns make that useful without overcomplication.

## Slice 8.4: Bordereaux Validation Engine

Goal: make bad bordereaux runs fail loudly before files are exported.

Requirements:
- Add validation result DTOs with severity, code, message, affected row key, and source entity ids.
- Implement validation rules from the roadmap:
  - missing policy number,
  - missing insured state,
  - missing transaction type,
  - missing premium value,
  - missing tax/fee value when the profile requires tax/fee output,
  - missing commission value when the profile requires commission output,
  - unissued policy packet,
  - accounting not posted,
  - transaction outside period.
- Define which rules are blocking versus warnings. Missing identifiers, missing financial values, unposted accounting, and outside-period rows should block export.
- A validation-only run may be recorded for audit, but export generation must not create a file when blocking errors exist.
- Store validation summary on `BordereauxRun`.

Primary files likely touched:

Tests required:
- One test for each roadmap validation rule.
- Blocking validation prevents file generation.
- Warning-only validation allows export.
- Validation summary counts errors and warnings correctly.
- Validation result includes enough source ids to navigate back to policy transaction/invoice.

Slice gate:

## Slice 8.5: CSV Premium Export And Download

Goal: generate the first traceable carrier/program premium bordereaux file.

Requirements:
- Add export generation for premium report profiles in CSV format.
- Create a `BordereauxRun` when export is requested.
- Run validation before export.
- If validation blocks export, leave the run in validation-failed status and do not upload a file.
- If validation passes, generate CSV with profile-defined columns in profile-defined order.
- Escape CSV values using the existing CSV journal export pattern.
- Upload the file through `IBlobStorageService`.
- Store blob path, file name, content type, row count, validation summary, generated by, and generated at.
- Add an endpoint for short-lived download URL.
- Keep XLSX out of this slice unless CSV is already proven and the same abstraction makes XLSX trivial.

## Phase 8 Completion Definition

Phase 8 is complete when:
- At least one real carrier/program premium bordereaux can be generated from policy transaction data.
- CSV and XLSX files are stored and downloadable through traceable run records.
- Validation blocks obvious bad reports before file generation.
- Tax/fee and commission report types work through the same run pipeline.
- Reconciliation tracks accepted, rejected, corrected, and resubmitted states.
- UI has no nonfunctional placeholder for the carrier reporting workflow.
- Authorization and data-scope decisions are documented.
- Backend tests and frontend build pass.
- Any go-live P0/P1 issue introduced or exposed by Phase 8 is resolved before release.
